# pkgdown overview

pkgdown builds a static website for your package documentation.

This reference explains what pkgdown publishes, where it gets that content, and
the workflows that keep it correct.

## What pkgdown publishes

Most pkgdown sites include:

- Reference index and function pages (from `man/*.Rd` generated by roxygen2)
- Articles and vignettes (from your package sources)
- README content and other top-level pages

Many sites also include:

- a curated reference index (grouped function/topics)
- an “Articles” section built from vignettes
- a “News” page built from `NEWS.md`

The main value is navigation + linking: search-friendly, interlinked docs rather
than isolated help topics.

## Sources of truth (what you actually edit)

pkgdown is a publishing layer. If something is wrong on the website, the fix is
almost always to edit the upstream source:

- roxygen comments in `R/*.R` → `devtools::document()` → `man/*.Rd`
- README source (`README.Rmd` or other source)
- vignettes/articles source files

Avoid editing generated site output as a “fix”.

## Configuring a site with `_pkgdown.yml`

pkgdown uses `_pkgdown.yml` to configure key site behavior.

Two high-leverage settings:

- `url`: the final, published URL of the site (used for correct links)
- `template`: site appearance (including Bootstrap 5)

Example:

```yaml
url: https://example.com/yourpkg

template:
  bootstrap: 5
```

You can also curate the reference index via the `reference:` field, so that
functions are grouped in meaningful categories instead of an alphabetical list.

Practical advice:

- Set `url` early. Many “broken link” issues are actually missing/incorrect `url`.
- Curate the reference index once you have more than a handful of exports.

Example skeleton:

```yaml
url: https://example.com/yourpkg

template:
  bootstrap: 5

reference:
  - title: Core
    contents:
      - starts_with("my_pkg")
  - title: Helpers
    contents:
      - ends_with("_impl")
```

## Structuring content (reference, articles, news)

pkgdown content typically comes from these sources:

- **Reference**: `man/*.Rd` generated from roxygen2.
- **Articles**: either vignettes (ship with package) or pkgdown-only articles.
- **News**: `NEWS.md`.

Decision rules that keep sites maintainable:

- If it must be checked and shipped: use a **vignette**.
- If it’s too slow/heavy or needs extra tooling: use a **pkgdown-only article**.
- If it’s “how to use one function”: keep it in **help topics** + short examples.

Related: [vignettes-vs-articles.md](vignettes-vs-articles.md)

## Local iteration workflow

### Local iteration

- Fix docs at the source (roxygen/README/vignettes).
- Rebuild the relevant surface:
  - `devtools::document()` for reference docs
  - build articles as needed (vignettes/articles)
  - rebuild the full site when you need to validate navigation and linking

For a full local rebuild:

```r
pkgdown::build_site()
```

For faster iteration, you can often rebuild only one surface:

- After roxygen changes: `devtools::document()` then rebuild reference.
- After article/vignette edits: rebuild articles.

Common fast loop:

```r
devtools::document()
pkgdown::build_reference()
```

Or, when iterating on articles:

```r
pkgdown::build_articles()
```

If you’re debugging docs that must pass `R CMD check`, keep `devtools::check_man()` in the loop.

## Publishing workflow

Use GitHub Actions to rebuild and publish the site (recommended via
`usethis::use_pkgdown_github_pages()`).

Recommended separation of concerns:

- **Checks workflow** (`check-standard`): validates the package.
- **Website workflow**: builds and deploys the pkgdown site.

This avoids “website issues” making check look broken, and keeps CI logs focused.

Common publishing strategies:

- Deploy to a `gh-pages` branch.
- Deploy to `docs/` on `main`.

Pick one and stick to it. Mixing approaches usually causes confusion.

If you’re using `docs/`, ensure GitHub Pages is configured to serve from `docs/`.

## Dependency discipline for websites

Website builds often need packages that you do not want as runtime dependencies.

Practical pattern:

- Keep runtime dependencies in `Imports`.
- Keep optional runtime features in `Suggests` and guard them.
- Record website-only tooling in `DESCRIPTION` under `Config/Needs/website`.

Example:

```
Config/Needs/website: pkgdown, downlit
```

Then configure CI to install website needs only in the website workflow.

## Troubleshooting

### The site builds, but links are wrong

Common causes:

- Missing/incorrect `url` in `_pkgdown.yml`.
- You preview locally at a different base path than production.

Fix:

- Set `url` to the real published site URL.

### Missing functions in reference index

Common causes:

- You changed roxygen but didn’t run `devtools::document()`.
- The function isn’t exported.
- `reference:` config excludes it.

Fix:

```r
devtools::document()
pkgdown::build_reference()
```

### Articles/vignettes fail during site build

Common causes:

- Vignette depends on packages not declared.
- Heavy/slow computations in vignettes.
- Network/credentials required.

Fix:

- Move heavy/non-portable content to pkgdown-only articles.
- Make dependencies explicit and optionality explicit.

### Website build fails on CI but works locally

Common causes:

- Local has extra packages installed.
- CI doesn’t have system deps or credentials.
- CI is building in a different directory/branch strategy.

Fix:

- Ensure website workflow installs `Config/Needs/website`.
- Keep website workflow separate from check.
- Treat the CI log as authoritative and reproduce locally.

## Common pitfalls

- Mixing check-sensitive content into vignettes (slow, network, heavy deps).
- Drifting docs: code changes without re-running `document()`.
- Unclear dependency boundaries: vignette/article depends on packages not recorded
  appropriately in `DESCRIPTION`.

If you’re deciding between a vignette (ships + checked) and a pkgdown-only
article, see `vignettes-vs-articles.md`.
